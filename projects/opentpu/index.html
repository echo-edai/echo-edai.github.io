    01 / 01 / MACHINE MODEL

    先建立机器模型：这里的 NPU core 是什么

    openTPU 是由命令驱动的张量处理 slice，不是运行普通 CPU 线程的通用处理器。先把命令、计算和存储三条边界画清楚。

    一张全图：主机、板级外壳、slice、运算单元

    主机通过 PCIe 把程序、权重、输入放进板载 DRAM，再用控制寄存器启动。otpu_board 包装一个或多个 otpu_slice，每个 slice 有自己的 IMEM、TMEM、ACT RAM、sequencer、DMA、MXU、quantizer 和 VPU。一个 sequencer 发命令，五类执行单元可以重叠工作；数据大多在显式地址的存储之间搬运。

    把 slice 称作本项目的“张量计算核”有助于理解，但它没有 NaplesPU 那样的硬件线程、通用向量寄存器文件、缓存目录和 mesh router。openTPU 的 LANES 是 VPU/TMEM 并行通道，MCOLS 是 MXU 并行驻留行数，二者不是同一个参数。

    Host / PCIe → otpu_board → otpu_slice × S
                         ├─ sequencer + IMEM + dispatch window
                         ├─ DMA ⇄ private DRAM
                         ├─ QACT → ACT RAM → MXU → TMEM
                         ├─ VPU ⇄ TMEM
                         └─ collective ⇄ every slice's TMEM
    SOURCE

    三种数据存储和一种指令存储

    空间寻址单位主要内容主要读写者
    DRAM字节权重、输入输出、程序、量化 scale、状态主机、DMA、MXU、QST

    最常见的地址错误是把 TMEM word address 当成 DRAM byte address：一个 FP32 元素在 DRAM 中地址加 4，在 TMEM 中地址加 1。容量同样必须带单位：TMEM_WORDS=65536 是逻辑数据 256 KiB；IMEM_WORDS=32768 是 32-bit words，所以是 4096 条 32-byte 指令。

    SOURCE

    为什么显式 scratchpad 有利于可预测的数据流

    缓存依靠 tag 比较、命中/未命中、替换、回填把一块内存透明地映射到较小存储；scratchpad 则由程序明确选择本地地址并安排搬运。TMEM 是后者。软件编译时分配中间张量位置，生成 LD、QACT、MM、VOP、ST，硬件保证这些命令之间的依赖与端口契约。

    优势是 tile 生存期和复用可由编译器安排，省去通用缓存替换与一致性控制；代价是容量、bank 冲突和搬运必须认真处理。TMEM 中某个变量被覆盖，不会自动从 DRAM 补回来；地址分配错误也不是“cache miss”，而是错误结果。自己写最小 NPU 时，可以先用同步 RAM + 显式 DMA 建出这条路线，再考虑缓存。

    SOURCE

    不把不存在的结构画进项目

    已核对的 top/slice/board 生产层级没有通用 mesh NoC，也没有以缓存行 sharer/owner 为状态的 directory_controller。otpu_coll 是中心 collective 通路，TMEM 的读口副本是同一逻辑 scratchpad 的物理复制，DRAM adapter 的 A 读复用/预取是局部优化；这些都不能改名成 MESI 目录。

    学习 NoC 和缓存一致性仍然有价值，但应作为设计扩展：如果要把多个 slice 改成共享地址的 coherent cores，需要新增缓存、home 映射、目录、探针与响应网络、瞬态和死锁规则。当前 openTPU 用私有 DRAM、显式 GATHER/BAR、主机/设备 ordering 合约处理跨单元协作。

    SOURCE

    02 / 02 / PARAMETERS & ELABORATION

    用 target 读架构：默认值不是板卡配置

    每个参数都改变一组端口、RAM 或调度约束。以固定提交的 ypcb-00338:m4 为主线，同时识别测试默认与实验变体。

    m4 的架构参数：先记住有单位的量

    targets/ypcb-00338.toml 的默认 variant 为 m4：S=1、D=128、MCOLS=4、ACT_ROWS=16、ACT_BLOCKS=128、TMEM_WORDS=65536、IMEM_WORDS=32768、LANES=8、DRAM_BYTES=4 GiB。D 是 INT8 元素/字节的 block 深度，不是总线“位数”；DRAM B 宽度是 D×8=1024 bit。

    ACT 的逻辑量化数据容量为 16×128×128=262144 bytes，scale record 容量为 16×128×8=16384 bytes，合计 272 KiB；这只是逻辑内容量，不等于 FPGA BRAM 实占。m8 变体把 MCOLS 和 MXU_E 改为 8，TMEM 改为 131072 words，不能把它的容量与 m4 的实现数字混在一起。

    SOURCE

    m4 的微架构参数：单拷贝、replay 与 2× 时钟

    当前 target 的 TMEM_IMPL=3、TMEM_NSB=2、TMEM_RPL=true、TMEM_TDP=true、TMEM_GST=true、TMEM_PMP=1，表示每 bank 两个 subbank 的单拷贝存储，读冲突通过 replay，真实双端口 RAM 以 2× core clock 使用。不能用 otpu_tmem 的参数默认值 IMPL=0 描述当前生产 target。

    同一 target 还有 WIN=16、FIFO_DEPTH=1024、MXU_IMPL=2、MXU_CL=16、MXU_E=4、SEQ_WC=true。源码注释保留 EXPERIMENTAL 字样，但 target 已选用这些配置；应分别说明“机制在源码中的标注”和“当前 target 的选择”，不要由标签推断是否启用。

    SOURCE

    仿真顶层与板级顶层各回答什么问题

    otpu_top 默认 S=1、D=32、MCOLS=8，服务于仿真。AXI=0 选固定延迟行为 DRAM；AXI=1 用 native adapter 加随机 stall/latency 模型；AXI=2 把 adapter 接到更接近实际 LiteDRAM 的仿真通路。这几个名字是本项目历史参数，AXI=1 并不意味着内部仍用旧 MIG AXI adapter。

    真实板卡从 otpu_board、板级 FPGA top 和 target 派生参数进入，包含主机控制、校准、时钟域、DRAM channel 和 trace。ASIC top 则接技术 RAM/DSP 与不同平台包装。先选问题再选顶层：算术差异查 ISA/单元，背压查 native memory 模型，时序闭合查实际 FPGA flow。

    SOURCE

    参数的约束比参数值更值得学

    MXU 要求 D 能按链分组、只接受当前 systolic IMPL=2、ACT_ROWS 至少 MCOLS；ACT RAM 要求 ROWS 是 MCOLS 的倍数并满足分组条件；DMA buffer 深度必须是至少 2 的 2 次幂；异步 FIFO 深度至少 4 且为 2 次幂。改一行 TOML 不保证组合合法。

    自己设计参数化 RTL 时先把可合法化的集合写成 elaboration checks，再写测试矩阵。例如测试 D=32/128、MCOLS=2/4/8、ROWS=MCOLS/2×MCOLS 时要同时改变地址宽度、replay 次数和 FIFO 容量；仅检查“综合能过”不能证明寻址和尾 mask 正确。

    SOURCE

    03 / 03 / FETCH · DISPATCH · ISSUE

    发射不是执行：把 sequencer 拆成可理解的状态

    从 256-bit 指令到五类独立单元：取指、地址解析、窗口分配、依赖跟踪、开始和完成有不同的时刻。

    指令格式与标量寄存器的角色

    指令长 32 bytes，除 opcode/flags 外包含多个地址、长度、stride 字段。cmd_t 保存已经加过 R[ra]/R[rb]/R[rc] 的字段；单元收到的是解析后的命令。16 个 32-bit 标量寄存器负责地址、循环计数和少量运行控制，不是 FP32 张量寄存器文件。R8..R15 可由主机参数初始化。

    NOP、LI、ADDI、LOOP 由 sequencer 内部执行；LD/ST/DSTEP/STREAM/WAITW 去 DMA，MM 去 MXU，QACT/QST 去 quantizer，VOP 去 VPU，BAR/GATHER 去 collective。RLD 使用 collective 的本地读口，但不发给跨 slice collective 状态机。自己实现时先定义命令结构和单元映射，避免各模块重复解析字段造成语义漂移。

    SOURCE

    同步 IMEM 为什么需要看前一条地址

    FPGA block RAM 的读是同步的，不能把 PC 组合地连到 RAM 后当作当拍指令。这里用 fa 预先取下一条、ir 寄存当前指令；reset 后 ir_v=0，因此开始有填充延迟。一个 D-byte 行能装 D/32 条指令，D=128 时每行 4 条。

    这不仅是功能设计，也是时序设计：决定窗口能否接收的信号影响 RAM 的 read enable，而尽量不经过下一取指地址多路器。LOOP 分两拍登记次数和 body 长度后再决定进入或跳过，减少地址路径上的加法组合深度。学习 RTL 时应追 enable 和 valid，而不是只看 PC++。

    SOURCE

    分派窗口里究竟存了什么

    窗口每个 slot 保存 valid、目标单元、年龄关系、started、依赖以及命令。older[i][j] 表示 j 比 i 老，是年龄矩阵；slot 编号本身不代表先后。一个 slot 空了可以被复用，因此不能简单选择最小编号作为最老指令。

    非 WAITC 路径把地址和长度计算划成 P/S/Q/C 阶段，得到 memory footprint 后才分配 slot。C 阶段在窗口满时 hold，背压沿上游 valid/advance 条件传播。执行开始时命令从每单元的 distributed RAM 副本读进寄存器，再由 ustart 告诉单元接受；命令存储与组合优先选择也要考虑 FPGA 时序。

    SOURCE

    完成不是“所有运算都同时结束”

    ustart[u]、urdy[u]、udone[u] 是命令级接口。每个单元的已开始 slot ID 排队到 uq，done 用队首找到完成 slot，再清掉其他 slot 对它的依赖。HALT 先停止接收后续指令，等待分派流水和窗口清空。

    单元之间可以乱序开始独立工作；每单元对外完成按它的开始顺序。VPU 内部能重叠多条不同延迟操作，因此开始条件还受延迟和依赖规则约束。不要把“ISA 语义等价顺序执行”误读成“RTL 每条命令完全串行”。

    SOURCE

    04 / 04 / DEPENDENCE TRACKING

    scoreboard 与 WAITC：同一种正确性，两种成本

    RAW/WAR/WAW 是对地址范围的冲突，TMEM bank 仲裁是同一拍端口资源冲突。两者必须分开理解。

    RAW、WAR、WAW 到底比较什么

    RAW：年轻命令读一个老命令将写的位置；WAR：年轻命令想写老命令尚未读完的位置；WAW：两者写同一位置。这里只读/只读不构成冲突；DRAM 与 TMEM 即使数字地址相同，也不是同一个空间。footprint 以半开区间 [lo,hi) 描述范围，相交条件是 a.lo < b.hi && b.lo < a.hi。

    例如 LD 写 T[0,128)，QACT 读 T[0,128)，MM 读 ACT row 0、写 T[256,320)，VOP 读 T[256,320)：形成 LD→QACT→MM→VOP。另一个 LD 写 T[1024,1152) 可能提前执行。若 footprint 太大，只会丢掉并行；漏掉一个范围则可能产生错误结果，因此实现倾向保守。

    SOURCE

    基础 scoreboard 的位图怎样解除依赖

    dispatch 时对每个有效老 slot 做 conflict()，把结果记入新 slot 的 sdep；MXU 另有只含 DRAM 冲突的 sdepd。单位选择候选时先看依赖是否消失，再按年龄找最老的 ready。done 产生 fin 位图，各 slot 清除已经结束的 producer。

    自己写最小原型可先固定四个 slot，每条命令只读写一个连续范围，用 N×N 依赖 bit 和年龄计数表示。验证应覆盖 slot 复用、同拍完成/分派、RAW/WAR/WAW、相邻不相交范围、不同空间以及 BAR。不要一开始就用推测执行和复杂 reorder buffer；本项目的重点是 memory footprint 调度。

    SOURCE

    为什么 MXU 分成 start 与 release 两次许可

    MM 有两种本质不同的资源依赖：权重从 DRAM 预取，驻留 ACT 操作数可能由尚未完成的 QACT 产生。sequencer 可在 DRAM 依赖清除后发 ustart，让 issuer 提前把权重和 scales 读进 FIFO；等所有依赖清除后才发 urel，许可 consumer 访问 ACT 和生成输出。

    若把 start 当成“立刻开始乘法”，就会误判 QACT/MM 之间的数据竞争。最小实现可用一条命令的 fetched/released/consumed 三状态，只有 fetched && released 才 pop 权重；再扩为两个 command slots，让下一命令读权重与上一命令计算/排出重叠。

    SOURCE

    当前 m4 使用 WAITC：编译器生成等待表

    target 的 SEQ_WC=true 映射到 sequencer 的 WAITC。每条指令旁边还有 64-bit wait entry，编码为 7 个 4-bit 字段与 VPU 前 31 条指令的依赖 mask；k3 保留为 0，k0/k1/k2/k4 等四类单元，k5/k6 专管 MM 预取对 DMA/quantizer 的等待。硬件打包宽度是 28+31 bits。DMA/MXU/QUANT/COLL 按本单元顺序开始/完成，计数表示还需等到某个历史位置；VPU 可挑最老 ready，故需要 mask 而不是单个累计完成数。

    WAITC 用软件已算出的信息替代地址范围比较，缩短 RTL 依赖路径；代价是程序镜像和硬件模式必须匹配。loader 不只搬指令，还要把 sidecar 送进对应 RAM。只给 WAITC 板卡加载裸指令，即使 opcode 编码正确，也违反运行契约。源码含用于检查 wait entries 是否覆盖真实 conflict 的仿真 assertions；本教学没有把该检查描述成已运行的整机验证。

    SOURCE

    两种“等待”不要混淆：依赖 ready 与端口 grant

    一个 VOP 可能在 scoreboard 上已 ready，并且已经 start，随后因为同拍 DMA 写了相同 TMEM bank 而被 hold。前者决定命令是否可以开始，后者决定其流水某一拍能否前进。前者跟命令的数据生存期有关，后者跟 RAM 的物理端口有关。

    自己写 RTL 时为两类事件单独计数：等待 producer 的周期数和请求 bank 但未获 grant 的周期数。若把所有停顿合并为 busy，就无法判断加大 MXU、增加 TMEM 端口还是改软件调度哪一项有用。

    SOURCE

    05 / 05 / SCRATCHPAD MICROARCHITECTURE

    TMEM：bank、复制、replay 与真实 RAM 端口

    用显式 scratchpad 学习多端口存储的实现成本，比把每个并行访问都写成数组读更接近真正硬件。

    bank mapping：地址为什么决定并行度

    TMEM 有 LANES 个 bank，bank = word_address mod LANES。LANES=8 时，连续 8 words 跨过所有 bank，适合每周期 8 元素的 VPU；stride=8 的一组地址却全落同一个 bank。逻辑容量足够不代表端口带宽足够。

    连续向量端口可用 barrel rotator 将 lane 对齐到 bank：若起始地址 mod 8=3，lane0→bank3、lane5→bank0 并跨到下一 bank row。MXU epilogue 写多个输出行，地址可能不连续，因此保留通用 crossbar。代码对本应连续的端口和同端口 bank 冲突有仿真检查，避免用不合法行为得到虚假性能。

    SOURCE

    IMPL0：用物理复制换多读口

    普通 FPGA BRAM 没有八个任意读端口。IMPL0 给不同读口做多份逻辑相同的数据副本，每个副本有 LANES banks；所有写广播到所有副本。这样不同读口大多不争 RAM，只剩同 bank 的写端口限制。guest ports 则共享 host port 的副本以省资源。

    这不是缓存副本：没有不同 tag、替换或延迟一致性的协议，写同时传播到全部复制体，它们表达同一块 TMEM。好处是简化读仲裁，代价是 BRAM 成本随读口数增加。自己实现时可以先做 2R1W RAM，两份 1R1W/SDP RAM 同写、分别读，再扩展 bank 和 bypass。

    SOURCE

    IMPL1：较少副本需要按 copy/bank 仲裁

    06 / 06 / QUANTIZATION & STATIONARY DATA

    量化与 ACT RAM：计算开始前的数据准备

    矩阵单元并不直接把 TMEM FP32 喂进 INT8 乘法器；QACT 和 scale records 把两种数值表示连接起来。

    QACT 与 QST 为什么是两条命令

    QACT 将 TMEM FP32 行量化成 ACT RAM 的驻留 INT8 操作数，供后续 MM 复用。QST 将 TMEM FP32 量化并写入 DRAM byte 数据及 scale rows，适合量化缓存或下一次作为 streamed operand 读取。它们共享 quantizer，但目标端口、布局和完成条件不同。

    量化不仅是截断为 8 位：每行求 amax，scale S=amax/127，分组 offset d 帮小幅值组利用更多 INT8 级别；值经过可选 row/column prescale 再舍入。零行、溢出和舍入边界必须服从 ISA 的数值语义。用普通浮点库的近似输出替代，可能在阈值边缘量化到另一个整数。

    SOURCE

    为什么先求 max，再量化：两遍和 row buffer

    在读完一行之前不知道 amax，因此基本量化要两遍读：pass0 做 prescale、abs、chunk max、行 max 和 scale；pass1 用 scale/offset 再读数据并生成 INT8。二者间要处理倒数计算延迟和不同组的 max 存储。

    XD>0 时，可容纳的 QACT 行把 prescaled chunks 放进 row FIFO，第二遍从 FIFO 取，从而省一次 TMEM read 和 prescale。最多四行在两遍之间，用 row-bank 保留 scales/group maxima，并在 read 发出时预留 FIFO credits，防止不可背压的数据回包把缓冲挤爆。这个优化以额外 RAM 换 TMEM 带宽，不能简单算作“quantizer 每拍恒定完成 LANES 个结果”。

    scale unit：倒数也有可验证的操作序列

    otpu_qscale 使用种子、两次 Newton 迭代和修正来求 reciprocal，再生成 S 和 inv。这里的 fp_mul/fp_add 是项目定义的 binary32 路径，包含 round-to-nearest-even 和 flush-to-zero 规则；固定运算顺序是 bit-exact 比对的基础。

    自己实现时先写 Python bit-level reference，确定每一步舍入，再把每级 pipeline 的 data、valid、row tag 和 enable 一同延迟。只延迟数值而漏掉 tag，会把上一行 scale 用在下一行数据；遇到 gnt=0 时必须整体 hold，而不是只有主计数器停。

    ACT RAM 的形状与写读安全

    ACT RAM 逻辑形状为 ROWS×BLOCKS×D bytes；每 (row,block) 还有 64-bit record {da3,da2,da1,da0,Sa}。quantizer 每拍写 LANES 个连续字节，MXU 每列取一个完整 D-byte block 和 scale。MCOLS 小于 ACT_ROWS 时，以 group 选择复用物理列存储。

    07 / 07 / SYSTOLIC MATRIX ENGINE

    MXU：从一个点积到真正的流水矩阵单元

    跟着一份 streamed weight chunk，穿过预取、ACT reuse、整数精确累加、scale epilogue 和 TMEM drain。

    MM 的矩阵方向与驻留行复用

    把 ACT 的 M 行看作 A[M,K]，DRAM streamed operand 的 N 行看作 W[N,K]，输出是 A×Wᵀ，形状 M×N。每次从 DRAM 读一个 D-byte 权重 chunk，可与至多 MCOLS 条 ACT 驻留行做点积；这就是减少权重流量的复用来源。

    D=128、MCOLS=4 的 INT8 情况，一个计算 advance 最多涉及 4×128=512 个 INT8 乘积，但 advance 会受 FIFO、scale、命令边界和 drain 限制，且不同数据格式有不同节奏。不能将这个乘积直接标为每秒实测算力。先计算访存量与理想上界，再用计数器找真实空泡。

    systolic 不是必须画成方形 2D 网格

    本实现把乘积沿 DSP cascade 链传递，CLS=min(CL,D/8)，每组 D/8 元素由一条或两条链产生整数 group sum。各列错开一拍，列端再按 block/group scale 对齐、累加，最后 deskew 回到同一输出行。

    关键是局部连接、逐拍传播和流水重用，不是图上有没有 16×16 正方形。真实技术 otpu_pe / otpu_mxce 在 generic、xilinx7、xilinxus 目录有相同接口的不同实现；当前 target 选择 Xilinx7 DSP48E1。自己写最小版先做 4 元素链，给每个值标 k 和 valid，看第 k 个乘积在何拍到列端，再扩 MCOLS。

    整数累加与 FP32 epilogue 分开的原因

    MX 数值先对 INT8 激活、不同权重格式的 group sum 做整数缩放，整行保留 48-bit 精确累加；最后只对每个输出做 i2f48，再乘权重行 Sw 和激活行 Sa·2⁻ᵂ。这样大量 MAC 不需要每次 FP32 舍入，scale 又能在最终恢复幅值。

    epilogue 由 E 条共享 lanes 排出，MXU_E 可以小于 MCOLS。m4 显式 E=4，恰好匹配四列；模块默认 E=0 则推导为 MCOLS/2（至少 1）。ACC/ASCALE 会读旧 TMEM 做 read-modify-write，RMAX 另写行最大值；这些额外范围必须进入 scoreboard，否则“矩阵结果正确但后处理冲突”仍会出错。

    SOURCE

    issuer、FIFO 和 consumer 如何吸收 DRAM 延迟

    issuer 负责读 weight chunks 和 scale lines，并为每笔 scale 请求保留 tag；consumer 只在一整行所需 chunks/scales 都已到位且命令已 release 时开始。这使一行进入阵列后不在中间被 DRAM 空泡打断，阵列无需逐级 clock-enable。

    两条 command slots 让较年轻命令预取与较老命令 drain 重叠；结果 FIFO 把整数阵列与受 TMEM grant 控制的 epilogue 分离。三个缓冲不能混为一个 FIFO：输入 chunk/scale FIFO 解决外存延迟，command queue 解决命令重叠，result FIFO 解决输出背压。

    SOURCE

    ACT_ROWS 大于 MCOLS：权重本地 replay

    m4 可一次 MM 指定最多 16 条驻留行，但只有 4 个物理 columns。一个 streamed row 在 FIFO 内被消费 ceil(M/MCOLS) 次：前几组只移动读位置而不释放 chunks，最后一组才真正释放。因此同一权重从 DRAM 只流入一次，却服务所有 M 行。

    这要求整条 streamed row 的 chunks 放得进 FIFO；源码显式检查 M>MCOLS 时的 KB/DEPTH 约束。区别于 TMEM 的“丢读重放”：这里是有意计算复用，TMEM replay 则修复物理读冲突。两者都叫 replay，但数据、触发条件和正确性证明完全不同。

    SOURCE

    4-bit、PAIR 与输出 bank 冲突

    4-bit 权重的一个 D-byte chunk 装两块，通常分两次 advance 消费；PAIR 在 2M≤MCOLS 时用两组 columns 同时处理低/高块，再在入结果 FIFO 前把两份整数相加。它利用闲置列提高小 M（尤其 decode）时的数据吞吐，但不是“所有 4-bit 矩阵都自动快两倍”。

    输出 stride ors 也影响速度。相邻物理 columns 写不同输出行，若 ors 是 LANES 的倍数，它们可能全命中同 bank，drain 一拍只能写较少结果。drain_run() 按 gcd(ors,LANES) 计算无冲突 run；这是软件布局能显著影响微架构利用率的直接例子。

    08 / 08 / VECTOR & STREAM COMPUTE

    VPU、归约和 stream engine：矩阵之外的工作

    Transformer 中的 norm、softmax、非线性和状态更新都需要矩阵单元之外的微架构。

    VOP 把 tile 映射到 lanes

    VPU 每次沿 TMEM tile 的一行处理 LANES 个 FP32 元素。A/B 可取完整 tile、每行广播、每列广播或标量 immediate；函数决定读哪些端口、走哪些槽位以及写回延迟。COPY/FILL/MAX 等也要经过地址和写回通路，并非“零成本指令”。

    tile 的 rows、cols、stride 与 lane mask 控制尾部。若 cols 不是 LANES 整数倍，最后一组必须禁用越界 lane；读 mask、写 mask 和归约中填的零/负无穷不能混用。自己写最小 VPU 时从 ADD 和 COPY 开始，先验证非对齐起始地址与尾 mask，再加广播。

    复合函数是固定浮点操作程序

    EXP2、RECIP、RSQRT、LOG2 被实现成固定 fp_mul/fp_add 序列：多项式、Newton 迭代和修正，近似误差与运算顺序都属于 ISA 约定。无 stream engine 时，一部分 long lanes 有多级 slot chain；短 lanes 只支持较简单函数，故 composite issue 宽度可能是 CL 而非 LANES。

    有 stream engine 时，COMP8 可让八 lanes 复用 slot0 和 tail 的部分 stage，按微码多次迭代。函数较长不必然意味着每元素独占整个单元直到结束，要看 issue 节奏、循环资源和 write order。用一个统一“VPU 每周期 8 ops”估算 softmax 会严重失真。

    归约为什么不直接写 for 循环相加

    FP32 加法不满足结合律；把一串数改成另一棵树可能改变 bit pattern。RSUM/RSSQ/RDOT 按固定 64 partials 的 isum_64 顺序：lane 负责若干 partial，流水 adder 形成 RL=64/LANES chunks 的反馈循环，再按固定树折叠。RMAX/ARGMAX 用比较树，argmax 在相等时选低 index。

    RDOT 先存每行结果，最后集中写回，可避免流式读取时与 DMA 的 TMEM 写竞争。自己实现先在 reference 中明确求和顺序与 padding，再做流水；只比较小整数和不足以发现浮点归约错误，必须加入大/小数混合、抵消、+0/-0 和边界舍入。

    WBUF 与前后端分离：背压不是随便停一拍

    基础 VPU 在 TMEM grant 低时整个计算进度 hold；WBUF 让 grant 只弹出缓冲头，内部前端靠已登记的 room enable 继续。读 replay 会在下一周期 hold 前端，后端按延后一拍的 en_b 对应停下，保证归约反馈、metadata 与数据仍同一节奏。

    这类设计的正确性来自“每一个 advance 都对应一份有效输入和足够的输出空间”。自己加 buffer 时要把所有 in-flight writes 算进 credits；不能只看 FIFO 当前不满，就忽略流水中下一拍还会到来的结果。源码的 front/back 描述值得逐句对着寄存器副本看。

    STREAM 如何借用 VPU 做状态矩阵更新

    DSTEP/STREAM 由 DMA 驱动 DRAM 状态数据，先拉高 ss_req，等待 VPU 的 VOP 全部排空、ss_gnt 许可，随后 DMA 填向量/标量，再逐 segment 推入 SE。VPU 的 slot0 reduction 和 tail 进行 dot、更新和输出，结果 segment 回 DMA 聚合后写回 DRAM，row output 回 TMEM。

    这让 Gated DeltaNet 等状态更新绕过“每次先搬整矩阵进 TMEM”的成本。它也意味着 SE 与普通 VOP 共享资源，不是可以永远与 VPU 并发的独立第三处理器。硬件只支持 STREAM 描述符的子集；新增描述符语义要同步 ISA、reference、DMA、SE 和测试。

    09 / 09 / MOVEMENT & BACKPRESSURE

    DMA：请求可以拒绝，响应却不能丢

    搬运模块的难点不是地址加法，而是在任意延迟、背压、mask 和写完成下保证每个字节恰好出现一次。

    chunk 与 segment：两侧宽度不同

    DRAM B 一次搬 D bytes，TMEM 一拍搬 W=min(D/4,LANES) 个 words。D=128、LANES=8 时一个 chunk 是 32 words，要拆成 4 个 8-word segments。DMA 对 transfer 触及的每个对齐 chunk 只请求一次，首尾 partial segment 用 mask 保留所需 words。

    LD 把回来的 chunk 放 buffer，之后按 segment 写 TMEM；ST 从 TMEM 逐 segment 收集成 chunk，附 word mask 后写 DRAM。设计中地址、word mask、buffer slot 和数据必须作为同一事务推进，单独给 b_addr++ 而忘了 tail mask 是典型 bug。

    SOURCE

    read credit：在发请求时预留响应空间

    DRAM read response 没有反压，不能说“回包时 FIFO 满了就让它等等”。DMA 发请求的当拍先 reserve 一个 chunk slot，只有剩余 credits 足够才继续读。buffer occupancy 包含已经回来和尚在路上的数据，不能只数当前 FIFO valid。

    最小原型可维护 issued、received、consumed 三个单调计数，约束 issued−consumed≤DEPTH、received≤issued、consumed≤received。固定延迟测试很容易遮住问题；随机拉低 request ready、随机但保序延迟 read response、长期停止 TMEM grant 才能验证缓冲是否真的安全。

    SOURCE

    ST 完成要等写被内存接收

    ST 可能把最后一个 chunk 交给 slice 的输出寄存器，但写仍在 adapter queue 或 memory controller 中。故 DMA done 要等 wr_idle，系统状态还要计入 slice 自己停留的 SW/B requests。否则主机一见 HALTED 就读取结果，有可能看见旧内容。

    ST 把收集好的 chunks 成 runs 连续发出，降低 DRAM read/write turnaround：DMA 有 B 口优先权，发一段写期间不夹杂 MXU 的 weight read。这里既有正确性上的完成 fence，也有性能上的请求批处理，应分别观测。

    WAITW：主机与正在运行的程序握手

    WAITW 周期读一个主机写的 DRAM word，比较条件成立才交付到 TMEM；不成立等待指定间隔再读，可设置 timeout。成功时会触发 a_inval，避免后续 MXU 的 scale read 复用到主机刚更新前的旧 A-port 数据。

    这种显式同步不是硬件 coherent cache：主机必须先写所需数据，最后写门铃 word；设备在 WAITW 成功后再读这些数据。自己实现需要定义 timeout 与在途 response 的竞争：本源码允许已经在路上的读若满足条件则正常完成，否则超时且不写 TMEM，避免半完成状态。

    10 / 10 / DRAM ADAPTER & CHANNELS

    从逻辑 DRAM 到两路 DDR：局部缓存与一致性的边界

    地址散列、scale 预取、partial writes、ordering 和 CDC 共同决定真实板卡能否喂饱计算核。

    A、B、SW 三个接口为什么分开

    B 搬 D-byte 数据 chunks，DMA 优先于 MXU 权重流；A 为 MXU 读 scale 所在的 32-byte line；SW 接 QST 的 byte-enabled scalar writes。把 QST 写从 A 分离，避免大量量化字节存储阻塞 MXU 的 scale reads。

    slice 先寄存 A/B/SW 输出，request valid 和 payload 在未 ready 时保持；B 的回包也寄存一拍，并用 tag 路由 DMA/MXU。注意 req/rdy 是本地协议，不应套用“请求打一拍就一定收到了”的假设。自己写时为每口规定 accept=req&&rdy，要求 ready 只依赖登记状态，减少组合环。

    SOURCE

    64-byte beat 与 channel hash

    D=128 的一个 chunk 被拆成两路 channel 各一个 64-byte beat。未 hash 时 c=b mod 2；CHASH 开启时 channel 还 XOR chunk index 的 parity，让某些 2 的幂 stride 访问不总压在单路 DDR 上。主机填充/读出 DRAM 必须使用相同地址映射。

    这属于存储通道交织，不是 NoC 路由或 cache home mapping。自己实现先写无 hash 的地址变换及逆变换，再验证任意 byte address round-trip，最后加 hash 并测试顺序流、矩阵转置 stride 和 partial beats。

    SOURCE

    A-port 复用是局部 scale buffer，不是 coherent hierarchy

    scale 读取有局部性：A adapter 可复用上次 beat，miss 时预取连续 APF beats；偏离 run 或写入命中会丢弃相关复用内容。它确实具有小缓存/预取缓冲的功能，但没有通用 tag hierarchy、跨 core sharer directory 或 CPU snoop 协议。

    尤其主机 XDMA 写不经过 native adapter，本地 buffer 无法自动观察所有主机写。故在 run reset、程序 load、WAITW 成功时 a_flush，依靠显式 ordering 防 stale data。理解这一点能帮助判断“为何没有 directory 仍要谈一致性”：这里需要局部新鲜度和可见性契约，不是 MESI 共享缓存协议。

    SOURCE

    partial write 的 read-modify-write 竞态

    DDR/ECC 控制路径不接受任意 partial beat 时，需先读旧 beat，再保留未修改字节、合并新字节、写完整 beat。若另一写在“旧读”与“整写”之间修改其他字节，整写会覆盖它，形成 lost update。

    SW queue 为分散 QST 写先做 fill read 并保序；QST footprint 覆盖所触及完整 beats，以阻止设备 B 写插入危险范围。主机同样不能写正在运行 QST 的 beats。channel 层的原子 partial RMW 会暂停对应命令流，代价可达一次 read latency；这解释了为什么逐 byte 写需要 gathering，而不是说 DRAM 天然按字节无代价写。

    SOURCE

    out-of-order 返回怎样恢复成顺序

    channel bridge 为避免单个 DRAM bank 阻塞所有命令，按 bank parity 分到两个 controller native ports。每个 port 保序，两个 port 的读可能相对乱序返回；bridge 在发出时为每个读预留 master FIFO slot，回包按 slot 写入，只有前面 slot 都完成才向上游前移 commit pointer。

    这不是 CPU 指令 reorder buffer，但思想相通：物理完成可乱序，接口承诺仍保序。读 tags 保存 master/slot 等信息；write data 必须在 controller 接收 write command 前已可用，因为 LiteDRAM 某些路径不会等你晚来的 valid。读代码时从“下游到底承诺了什么”反推上游 buffer，而不是只看总线名字。

    11 / 11 / INTER-SLICE COORDINATION

    collective 不是 mesh：多 slice 怎样协作

    先学当前中心式 BAR/GATHER 的数据和完成条件，再思考扩大规模需要哪些 NoC 机制。

    BAR 与 GATHER 的精确语义

    所有 slices 到达同一种 collective 才开始。BAR 只同步；GATHER 从每个 slice 的 TMEM 段读出，再广播写入所有 slices 的目标位置：T_all[dst+s*seg+r*drs+c]=T_s[src+r*srs+c]。单元维护 s/r/c 计数，按 LANES 个连续 words 组织流水。

    所有 slice 必须给出一致的 GATHER 目标形状/stride；源码在仿真中检查命令不一致。整体 grant 是每 slice 本地 grant 的 AND，所以任一 TMEM 口阻塞都可 hold collective。它不是让任意核随意 load 另一个核的缓存行，数据移动和同步都由显式指令触发。

    YPCB 的 Vivado flow 默认 COLL_GATHER=0（自 release r2），S=1 时只构建 otpu_coll_bar；遇到 GATHER 会报告错误。仿真顶层默认 COLL_GATHER=1，S>1 需要完整 GATHER。是否存在这条数据通路必须核对 flow 参数和 CAPS2，不能只看源码中定义了模块。

    SOURCE

    四状态机与 ACK 冷却周期

    C_IDLE 等所有 req，C_RUN 发读/写并排空流水，C_ACK 通知所有 slice 完成，C_COOL 防止尚未降下来的 req 被当成下一条命令。读请求、读数据、写寄存都是不同阶段；“发出最后一个读”不代表最后一个目标写已落下。

    自己写最小 barrier 时就应该保留请求/应答的完整握手：每个参与者持 req 直到 ack，controller 记录或等待所有 req，ack 后要求参与者撤销再复用。只写 ack=&req 容易重复确认；跨 pipeline/clock 时尤其危险。

    SOURCE

    BCU1525 跨 SLR：数据管线与 credits

    board 在 S>1 时把 slice 分到不同 SLR，控制和 collective 双向经过寄存级。otpu_coll_hub 与每 slice 的 otpu_coll_port 解耦长距离接口，本地端口自己争取 TMEM grant；写入通过队列/credits 控制。

    hub 收到 collective 内部 ack 后还要等待各 port 的 writes 真正 drain，才把 ack 送回 slices。已经确认但还跨线未降的 req 用 blk mask 防重复。这是 interconnect 学习的好入口：传播延迟使“远端现在 ready”不能直接等同“我这拍可以无限发”。但它仍是专门的中心 hub，不是 XY 路由 mesh。

    SOURCE

    从 collective 扩展到 NoC：要新增什么

    若自己要扩为 mesh，最小非一致性版本可定义 packet{dst,src,op,addr,len,txn_id}，加本地 network interface、每方向 FIFO、route selection、output arbitration 与 ready/credit flow control，先实现单 flit XY 路由和无环请求路径。GATHER 可以由软件分解成点对点传送加 barrier。

    不要只替换一条连线：需要证明背压时 packet 不丢、不重复、头尾不混，多个包公平前进，response 不被 request 堵死。加入 coherence 后还需区分 request/probe/response 的依赖或虚拟网络。本段是扩展设计任务；当前源码没有这些 router 或 directory 模块，应在自己的新目录实现与验证，不能称为上游功能。

    12 / 12 / BUILD A CORRECT SYSTEM

    复位、CDC、可观测性与从零实现路线

    一个能乘矩阵的组合电路与一个可稳定运行模型的系统之间，还隔着启动、停止、跨时钟与可复现验证。

    LOAD、RUN、HALT CHAIN 的完整生命周期

    主机先确认 controller calibrated，RUN=0 时写 PROG_ADDR/PROG_N 和参数，触发 LOAD；loader 等 rd_idle，防 stopped run 的旧回包被当成新程序，再按 chunk 写 IMEM 和 WAITC sidecar，完成后 RUN 拉高开始。停止 RUN 不会撤销 adapter 已接收的写；主机要等 WR_IDLE 再安全复用 DRAM。

    HALT CHAIN 在程序结束时拿标量寄存器指定下一段程序，让 slice 复位执行单元、装入新 IMEM 后继续；TMEM/ACT/DRAM 内容保留。它把设备侧循环扩展为多程序链，不能当普通 CPU jump：loader 与 memory ordering 仍参与。自己实现时写出 start/stop/load/chain 与旧读回包交叉的状态表，比先堆更多算子更有价值。

    SOURCE

    CDC：不能直接同步一整条数据总线

    core、DDR user clock、PCIe clock 各自独立。异步 FIFO 在本时钟域保存数据，用 Gray-coded pointers 经过两级同步器把“写到了哪/读到了哪”告诉对端；对端看到的是保守滞后的 occupancy，读 credits 必须按这个延迟计算。

    Gray code 保证计数每次加一只变一 bit；若一个周期计数加二，多 bit 同时变化会破坏假设。channel bridge 因此分别跨每 port 的单步 write counts，再在主域相加。复位两侧也必须协调，否则一边指针归零、另一边仍认为旧数据有效。RTL 的 ASYNC_REG 与 max-delay/bus-skew 约束属于实现的一部分。

    SOURCE

    先测什么：让每层有自己的 oracle

    最低层用 directed/random tests 检查 FIFO、RAM bypass、bank/replay、mask；算术层用 opentpu/fp32.py 的位级定义比对 FP 和量化；命令层用 ISA simulator 比对 TMEM/DRAM；整核再跑编译后的最小 matmul/norm/attention，最后才上模型和板卡。

    最有价值的测试会制造时序差异：随机拒绝 DRAM request、可变回包延迟、连续 SW partial writes、TMEM replay、在途写时停止 RUN、两个 slice 先后到 BAR。仅检查最终一个矩阵对了，不足以发现 reset/credit/deadlock。网页教学演示是解释工具；除明确列出实际运行记录外，不等于上游 RTL 的周期精确验证。

    SOURCE

    从现有计数器定位瓶颈

    板卡寄存器提供 CYCLES、ICOUNT、B_RD/B_WR/A_RD/SW_WR、B_STALL 和构建参数；free-running counters 包含 MXU_BUSY、MXU_MAC、VPU_BUSY、QNT_BUSY、DMA_BUSY、TMEM_DENY、DRAM_WAIT、MXU_STARVE。trace 可看到 dispatch/start/end 等事件，帮助区分“没有可用工作”和“有工作但等数据”。

    分析顺序是：先确认 target/CFG_HASH 与程序匹配，再看正确性，然后将总 cycles 分为依赖等待、输入 starvation、输出/端口背压和真实计算。decode 小 M 往往读权重占主导，prefill 多行更能复用权重但可能暴露 MXU 或 VPU 瓶颈。这里是分析方法，不把上游某次性能数字当成本次测量。

    SOURCE

    自己写一个最小 openTPU 风格核

    1. 定义契约。选 D=16/32、LANES=2/4，写指令语义和 Python reference；用 byte/word 单位区分地址。
    2. 先写搬运。同步 TMEM + LD/ST DMA，带 mask 和有界 read credits；随机背压仍严格保存数据。
    3. 加入量化和点积。先固定 row scale 和简单 INT8 链，再添加 scale records、整数累加和 FP epilogue；与 reference 位比对。
    4. 加入命令并发。四 slot 范围 scoreboard，覆盖 RAW/WAR/WAW 和 BAR；建立 start/done 规则后再做 MM start/release。
    5. 逐项优化。bank mapping、command/FIFO overlap、TMEM replay 或 WAITC 一次只开一项，并记录正确性和 cycles。
    6. 扩展系统。最初用单时钟行为 DRAM；最后接 native ports、CDC、主机寄存器和真实 controller。

    若目标是 coherent manycore，应单列 cache/directory/NoC 支线；它需要不同系统契约，不能靠给 scratchpad 改名完成。实现完成的标准不是画图相似，而是接口、状态、不变量和压力测试全部闭环。

    从 Python 程序走到一条硬件命令

    先把语言、编译、指令语义、RTL、板卡五层分开，再把它们连接起来。

    不是任意 Python 都会变成电路

    @ol.jit 包装的是一个可被追踪的 Python kernel。追踪时，传入的张量变成带地址、形状和布局的描述符；加法、load、dot 等调用在 Builder 中产生指令。普通 Python 控制流仍在主机上执行，例如 ol.static_range 会展开循环。这不是把任意 Python 自动综合成 RTL，也不是先生成 LLVM IR 再交给通用 CPU。

    理解时用两支笔：一支标记“此时主机正在计算常量”，另一支标记“此时向程序列表添加了设备指令”。这能解释为什么 program_id() 可在编译时返回 slice 编号，而设备 token 位置需要 RunVar 与地址寄存器。

    SOURCE

    五层契约：表达、存储、命令、语义、实现

    表达层是 language.py 的 API；存储层是 Tensor、QTensor、Tile、Stationary；命令层是 isa.Instr；语义层是 isasim.Slice.execute；实现层是 Sequencer 与各执行单元。一个操作只有在五层能够互相解释时才算读懂。

    例如 ol.dot(x,w) 先检查 w 是 DRAM 量化矩阵，x 若在 TMEM 则插入量化，再建立 MM 指令。模拟器按同一字段读取整数、尺度和结果地址；RTL 用这些字段驱动 ACT RAM、DRAM 和 MXU。不要只从函数名字推断数据实际在哪。

    项目目录各自回答什么问题

    14 / SOFTWARE / 02

    布局即数据搬运：四种对象的真实含义

    地址空间、stride、量化尺度与生命周期决定一段 kernel 能否执行。

    Tensor：DRAM 的视图，不是已加载的数组

    Tensor 保存 base、shape、strides、host 和 offset。base 是字节地址，而 strides 是元素数：沿一维前进 st 个 FP32 元素时，地址增加 4*st 字节。切片主要构造新的描述符，既没有搬运数据，也没有自动生成缓存。

    这就是为什么 ol.load(desc) 仍然必要。自己设计描述符时必须在字段名或类型中写清单位；“字节地址”和“32-bit word 索引”一旦混用，矩阵很小也可能恰好不崩溃，却在第二行开始读取错误数据。

    SOURCE

    QTensor：MXU 流式操作数的存储协议

    QTensor 指向 DRAM 中已经打包的量化矩阵，包含数据地址、尺度地址、形状、行字节步长 rs、尺度行步长 srs、D、格式 wf、块偏移 k0。当前格式包括 int8、int4、fp4 和 nvfp4；尺度记录不是一概“每块一个 float”。

    列切片不等于移动一个普通连续指针：必须同时保留正确的尺度起点、k0 和格式打包约束。parts 用于把列分片单独存放，tiles 用于 V 转置缓存的 token 分块。学习时把“逻辑矩阵坐标 → 物理字节 → 对应尺度”画成三栏，避免只看 shape。

    SOURCE

    Tile：TMEM 中间值和 bank-aware stride

    Tile 是 TMEM 中的 FP32 对象，其 base 和 row stride 以 word 为单位。TMEM 的低地址位选择 bank；MXU 一次流式行输出会把多个驻留行的结果写到 out + j*row_stride。当行步长是 bank 数的倍数，这些地址可能落到同一个 bank，减少并行度或触发实现约束。

    当前 dot 为多行、偶数 N 的新结果选择 N+1 的奇数 stride，并为 rowmax 预留空间。逻辑上仍是 M×N，物理上却有 padding。因此不能用 M*N*4 直接代表全部 TMEM 分配量。自己写布局器时应把 shape、stride、分配长度分成三个字段。

    SOURCE

    Stationary：驻留是一份有所有权的资源

    Stationary 表示已经被 QACT 写入 ACT RAM 的整数操作数。它跟踪 chunks、KB、owners、PAIR 与 qranges；owners 使编译器能发现物理区被覆盖。一个 Python 变量仍在，并不意味着其底层块永远未被其他操作重用。

    当前 ACT_ROWS 可以大于 MCOLS。板卡默认 ACT_ROWS=16、MCOLS=4，一条 MM 先把整条 streamed row 的 chunks/scale 放入 FIFO，各驻留行组重读同一组条目，最后一组再释放；更大的输入也可能拆成多个 chunks。旧文档写“至多 8 行”不能作为当前限制，rowmax 和 acc_scale 的限制又要单独看 dot 的检查。

    SOURCE

    QACT 范围影响数值与指令条数

    一个 Stationary 可以由多次 quantize_into 填充。每次 QACT 建立自己的量化范围及尺度；当前 dot 会按 qranges 产生 MM，并把后续部分加到已有结果。只检查最终整数矩阵的 shape 不足以还原语义，还必须知道哪些 K 块共用同一 Sa。

    自己实现时，让每个量化片段携带 [k0,k1) 与尺度 ID；合并前验证范围连续、没有未写块、没有错误覆盖。上游 Stationary.ranges() 就会拒绝缺口。测试应比较“一次整体量化”和“按规定范围分次量化”的差异，而不是默认它们永远相同。

    SOURCE

    生命周期分配：为什么临时变量命名会影响编译

    TMEM 分配以 Tile 所属 buffer 的存活为依据，使用 weakref 跟踪；next-fit 从游标后找空隙，尽量让新临时值远离最近仍在执行的地址。必要场景可用 best-fit 重试。ACT RAM 则在仍存活的 Stationary 占用之外做 round-robin 搜索。

    一些融合只对未命名的临时值生效，防止把调用者还会使用的中间结果改写。不要把 Python 垃圾回收理解为硬件执行已经结束：物理读写冲突仍由依赖机制排序。自己写第一版可用显式 free 和固定 buffer，验证正确后再实现 liveness。

    SOURCE

    编译器微观：一次追踪怎样生成程序

    不需要先读完两千行；抓住描述符、地址、分配、发射、收尾五个关口。

    从 Kernel.trace 到每个 slice 的程序

    runtime 先将参数放入 DRAM 并构造每个 slice 的绑定参数，再对 s=0…S−1 分别调用 trace。追踪期间 Builder 知道当前 sid 和 S，所以 SPMD 的 program_id() 是编译时值。相同 kernel 函数可以在不同 slice 产生不同的静态地址和 shard 行为。

    自己写一个最小编译器时，不必一开始建立复杂优化 IR。可以先用“操作对象列表 + 明确布局 + 指令构造函数”，保留源位置，把每个操作与输出指令一一对应。上游 Instr.src 也记录 kernel 源栈，便于 profiler 追踪来源。

    SOURCE

    Affine：让循环只占一个硬件 body

    Affine 表示常量与若干循环变量、运行时变量的线性组合，例如 base + i*block*4。编译器为合适的系数模式分配地址寄存器，循环末尾发射 ADDI，硬件指令读取寄存器加立即数。它不是任意表达式求值器：描述符大小若依赖循环且不能静态确定，就可能被拒绝。

    自己实现时先写出标准形式 c + Σ ai*vi，对键排序并合并系数，再做寄存器共用。必须处理循环退出的恢复和寄存器归零，否则第一次迭代正确、第二次错误是最典型症状。

    SOURCE

    ol.range 与 static_range 的代价不同

    static_range(n) 在主机展开，程序大小随 n 增长；ol.range(n) 追踪一次 body 并生成 LOOP，节省 IMEM，但带来地址寄存器、可变状态和循环边界约束。循环中要更新硬件 tile，使用 t.set(value)；给 Python 名字重新赋值往往只是改变追踪对象。

    比较同一个小循环的反汇编：展开版有几份 LD/MM，硬件循环版有几个 LOOP/ADDI？再观察 TMEM 峰值和 IMEM words。选择不是“循环越少越好”，而是在程序容量、寄存器压力与可调度性之间取舍。

    SOURCE

    局部融合是少搬一次数据

    融合并不是一句抽象的“更快”：exp2(a-b) 可以成为 EXP2SUB，省去差值 Tile 的写回和重读；RMSNorm 的平方求和可变成 RSSQ；quantize(x*cscale) 可在量化单元内融合列缩放；MM 的 RMAX 在结果排出时顺便得到行最大值。

    这些规则只在检查满足时触发。一个中间值若被用户命名并复用，就不能随意消除。自己添加融合时先写等价条件、别名条件、生命周期条件和数值舍入顺序；“数学等价”不保证逐位相同，尤其 add/mul 不是任意可结合的实数运算。

    SOURCE

    怎么增加一个自己的算子

    建议从已有 ISA 可组合的算子开始，例如 y=x*x+b：写一个 ol kernel，检查形状和广播，反汇编确认 load/VOP/store，再与独立参考函数比较。下一步尝试把它融合成新 VOP：先定义 opcode/字段/舍入顺序，再加 isasim、RTL、编码往返和边界向量，最后才让 compiler 发射它。

    最有价值的测试是“新算子应满足的契约”，如广播边界、alias、±0、极值、长度不是 lane 整数倍、读写重叠。只复制实现算法写另一份同样循环，很容易让相同错误同时存在于实现和测试。

    16 / SOFTWARE / 04

    ISA、指令模拟器与依赖：哪些行为必须一致

    功能顺序与硬件并行并不冲突；模拟器回答结果，RTL 回答时序。

    每条指令占 8 个 32-bit word

    Instr.encode 将 opcode 放在 w0 低 8 bit，四个寄存器编号各占 4 bit，flags 放在高 8 bit，后接 w1…w7。每条指令因此是 256 bit，即 32 字节。IMEM_WORDS=32768 表示 32768 个 32-bit word，即 4096 条指令，而不是 32768 条指令。

    自己设计 ISA 时，先固定字节序、符号解释、保留位、寄存器零值和非法字段的处理；再写 encode/decode 的往返测试。字段空间用完后的兼容成本很高，文档中的单位必须可直接用于 loader 长度检查。

    SOURCE

    R0、运行时参数与设备计算值

    机器有 16 个 32-bit 标量寄存器，R0 读取为零；启动参数进入 R8…R15。RunVar 把运行时值及其系数映射到参数寄存器，地址用寄存器加立即数；DevVar 则表示由设备运算得到的寄存器值。参数寄存器也会与循环地址寄存器争用有限资源。

    这解释了为什么同一模型换一种布局后可能“寄存器不够”，即使 TMEM 还有空间。自己实现时给寄存器显式角色与存活区间，避免仅按递增编号分配；循环内释放的寄存器尤其要检查下一次迭代是否仍会使用其旧初值。

    SOURCE

    顺序语义不是整台机器只能做一件事

    isa.md 用“每条指令完成后下一条开始”描述可观察的功能结果；isasim 也主要按指令推进。但当前 RTL 的依赖控制和多执行单元允许安全重叠。读性能时必须回到 Sequencer、目标 SEQ_WC、unit 完成和 TMEM/DRAM 冲突，不能把参考模型当成周期模型。

    自己实现时先做完全顺序核：发射一条，等待 done，再发下一条。通过对照后再加入多个 in-flight 槽，把每条命令的读写 footprint 作为依赖依据。这是一条可验证的演进路线；直接从并行窗口开始很难定位首次错误。

    SOURCE

    WAITC：把保守依赖分析搬到软件

    当前目标启用 SEQ_WC。waits.py 为每条指令建立旁路的 64-bit wait entry：多个 4-bit 计数用于有序单元的生产者距离，VPU 用 mask 指定可能乱序完成的生产者。MM 的流式预取与释放还区分不同等待点，不能只等待一个全局 busy。

    分析以寄存器区间与访问 footprint 保守覆盖可能地址，循环需要达到固定点。保守会损失并行度，漏掉依赖则会破坏正确性。该机制不是缓存一致性协议，也不是 docs/scoreboard.md 的工作负载估算模型。自己写第一版可先实现确定地址的 RAW/WAR/WAW，再逐步处理循环与运行时地址。

    SOURCE

    GATHER、BAR 与全局等待

    slice 的 DRAM 是私有的；跨 slice 通信通过显式 collective。模拟器遇到 BAR 或 GATHER 会把 slice 标成等待，由 Machine 统一推进匹配的 collective。语言层 all_gather 把各 slice 的 Tile 沿最后一维拼接并复制到所有 slice；all_reduce 当前由 gather 后的 VOP 加法组成。

    自己实现时要规定参与者集合、相同 collective 的匹配方式、目标地址一致性与完成条件。不能让一个 slice 永远跳过 collective 而其他 slice 等待它。测试应包含不同 slice 到达时间、地址解析差异和错序 collective，而不是只看两份相同程序。

    SOURCE

    量化、整数积与 FP32：数值也是架构的一部分

    少搬字节要付出怎样的精度与元数据代价？必须沿当前 MX 格式回答。

    不是简单的 float 除以一个 scale

    当前 MX 格式在行尺度之下使用块或子块的结构化尺度。int8 元素配合行 FP32 Sw 和块偏移；fp4/int4 还含子块乘数；nvfp4 使用其规定的 E2M1/E4M3 记录。4-bit 两个元素可打包进一个字节，但整体模型占用还包含尺度、对齐、KV 和其他表。

    因此“从 int8 变 fp4 等于全部显存正好减半”不成立。用 row_bytes 与 scale_bytes 计算实际格式字节，再在固定模型、上下文与目标上比较。旧 survey 结果和当前 MX 生产格式必须按版本区分。

    SOURCE

    激活量化的范围会改变误差

    QACT 把 TMEM FP32 转成 ACT RAM 整数及尺度；当前激活有每个 QACT 范围的行 Sa 和 D/4 子块偏移。若一个很大的离群值与许多小值共用尺度，小值可用的整数等级会减少。改变分块、按 head 分片或融合缩放时，要同步改变参考仿真中的量化范围。

    自己写量化器可先实现对称 int8：求绝对最大值、建立非零 scale、按明确规则舍入并饱和，然后逐个加入零行、极值、±0 与子块。不要直接使用语言默认 round，必须核实负半整数、溢出与 NaN 的处理。

    SOURCE

    矩阵积为何需要逐位参考

    MXU 先进行整数相关计算，再按规定尺度恢复并以 FP32 写回。不同实现在累加顺序、截断、偏移窗口和 epilogue 处可能产生不同结果。上游的 mx_matmul 及 isasim 不是随便一次 NumPy matmul 的替代名，而是当前数值契约的参考实现。

    自己写时至少保留三个结果：理想 FP32、按设备格式重建后的浮点参考、设备规定顺序的逐位参考。第一个量化精度，第二个算法对照，第三个抓 RTL 实现错误。三者不能混成一个“误差小于某阈值”。

    SOURCE

    FP32 运算不是完整 IEEE 754 实现

    当前契约固定 roundTiesToEven，输入和输出的 denormal 会 flush-to-zero；没有完整的异常标志与多舍入模式；倒数、平方根相关函数和指数采用规定近似。因此读到“FP32”时应理解存储格式和这里明确的算术规则，不能自动推出所有 IEEE 754 行为。

    softmax 使用 exp2，系数与运算序列固定；x*1 + -0 的零符号等细节也是逐位对照的一部分。自己实现浮点流水线时从独立加法器、乘法器和边界向量开始，再组合复合函数。数学恒等变换可能改变舍入结果。

    SOURCE

    判断量化改动是否值得：四种比较

    第一，设备与设备数值契约逐位参考比较，用来找实现错误。第二，量化后的模型与未量化模型比较，用来评估格式损失。第三，固定 token 上下文逐步比较 logits，避免一次 token 分叉导致后续输入也不同。第四，再测实际周期、流量和墙钟时间，区分设备算力与主机编译开销。

    不应从一个小矩阵误差推出完整模型质量，也不应只从生成速度推出回答质量。源码里的 validate 工具和量化测试提供入口；本课程中的公式和交互只是教学计算，不声称重新测量了上游模型结果。

    从 Attention 到整层模型：数据复用怎样写进代码

    沿 scores、online softmax、P·V、归一化逐步还原，不背一个抽象黑盒。

    QK 与 PV 使用同一个 dot，但布局不同

    QK 阶段：query 量化后驻留 ACT RAM，K 的 token 行从 DRAM 流入，得到 score Tile。PV 阶段：softmax 概率经过量化后驻留，V 的转置布局流入，得到 head 输出。数学里这两个矩阵乘法很接近，物理存储需求却不同。

    KV cache 的 K 更适合按 token 行，V 为 PV 读取而转置并可能按 token tile 存储。量化后的 V token scale 被折进 P 的量化，VT 可以作为 UNIT 流。自己写时先选固定 head_dim、固定 block 和单 head，再检查追加一个 token 后的四个区域：K、K scale、VT、V scale。

    SOURCE

    Online softmax 只保留 m、l、acc

    每个块先得到局部 scores，再更新最大值 m_new=max(m, block_max)，用 alpha=2^(m-m_new) 修正之前的累积；当前块概率 p=2^(score-m_new)。随后 l=alpha*l+sum(p)、acc=alpha*acc+p·V，最终输出 acc/l。

    不必保留整个 T×T attention 矩阵，这减少 TMEM 需求。代码的 acc_scale 把旧 acc 的修正放进 MM epilogue，避免额外完整读写。自己实现可先用实数/FP64 验证公式，再使用项目 FP32 规则；还要覆盖尾块全 mask 与所有值为负的情况。

    SOURCE

    软件流水：当前实现可用 depth=3 多缓冲

    当前 _attend_heads 默认 depth=3，预先把后续若干 score block 发出去，在其他 buffer 上完成 softmax 和 PV。它还能跨 head 提前准备 queries，让不同依赖链重叠。旧 compiler.md 的两块循环是一个讲解例子，不能替代当前源代码的全部调度。

    buffer 数量增加会延长 Tile 和 Stationary 的存活，消耗 TMEM/ACT RAM，并可能压低可容纳 query 行数。自己写流水线时先给每个 buffer 写清“生产者、消费者、最后一次读取、可重用时点”；仅交替两个数组名字并不保证没有覆盖。

    SOURCE

    因果 mask 与尾块是正确性路径

    Attention 不只是快速的满块路径。Bucket 处理运行时长度的最后部分，Additive 用 −0 和 −inf 的预置 score Tile 配合 MM ACC/RMAX，RowMasks 为 packed prefill 的每组 query 行给出不同可见 token 范围。尾部概率要补零到 D 的要求，以免把填充位置计入结果。

    自己验证时用非常小的两三行矩阵逐项列出可见位置；分别测 block−1、block、block+1、cache 末端和第一 token。先确保“被 mask 的 token 权重严格为零”，再观察优化是否保持与未优化路径相同。

    SOURCE

    Decode、Prefill、Batch 为什么遇到不同瓶颈

    单 token decode 的矩阵行数小，很多权重字节只服务少量乘法；prefill 把多个 token 行放在一起，可复用同一次流式权重读取，但会消耗更多 TMEM 和 ACT RAM，并需要正确因果 mask；batch 也可增加独立行，却有不同会话、KV 和公平性约束。

    增加 MCOLS 主要增加并行处理驻留行的能力，不会凭空增加 DRAM 带宽。增加 ACT_ROWS 可用 replay 复用权重，但每个流式 chunk 也需要更多处理拍。自己做性能模型应先数权重字节、KV 字节、算术次数、驻留行和 TMEM 峰值，再和 RTL 周期或板卡计数器比较，不能把理论峰值当作 tok/s。

    SOURCE

    SwiGLU MLP：shard、分块和 collective 在一处相遇

    MLP 先得到 gate 与 up 两个投影，向量单元计算激活函数及逐点乘，再进入 down 投影。当前 swiglu_down 可把下一个 chunk 的 gate/up MM 提前发射；多 slice 通过 all_gather 汇总各 slice 的中间片段，再累加 down 的对应列片。

    F chunk 受 D、权重格式、TMEM 容量、量化范围和 epilogue 吞吐共同约束。自己写一个两 slice 版本时，先用整数小矩阵手算每个 slice 负责的 F 范围，再标记 gather 后的拼接位置；最常见错误是把“按输出行分片”和“按归约维列分片”混为一谈。

    SOURCE

    运行时与板卡：程序以外还有一半系统

    从参数布局、启动、配置核对到回读，构造一条可复现的执行链。

    Host 参数怎样变成各 slice 的 DRAM 镜像

    runtime Input 被复制到各 slice；Weight 可以完整复制，也能按行或列分片，且每份在放置时量化；Output 分配结果位置；KVCache 把 head 按 slice 分配。place 产生 DRAM images、布局记录和每个 slice 的参数描述符，编译与回读依赖同一份元数据。

    DRAM 分配按 ALIGN=128 对齐，并检查容量。教学时不要对默认板卡 4 GiB 配置随意创建全尺寸零镜像：第一次执行宜显式用小 Config，避免只是为了一个小算子就分配大量主机内存。

    SOURCE

    compile、launch、collect 是三个不同阶段

    compile_kernel 放置参数并追踪程序；run 选择 ISA 或 RTL 后端；collect 根据 store 记录恢复主机输出，并能发现输出中从未被写入的元素。launch 只是编译再运行的便利封装。

    自己设计 runtime 时保留可独立保存的“程序 + 数据镜像 + Config + 元数据”。这样同一输入可以送入 ISA、RTL 和板卡比较，而不是每个后端偷偷重新量化或重新分配，导致测试实际上比较了不同问题。

    SOURCE

    三种配置入口不能互换

    Config() 是小型语义测试默认值，D=32、MCOLS=8、DRAM=1 MiB；target.config() 返回目标声明的真实架构与可选特性；board_config() 还支持环境覆盖，部分可选特性默认关闭。真实板卡则由 device_config 从 bitstream 信息读取。

    当前 YPCB 默认 m4：S=1、D=128、MCOLS=4、ACT_ROWS=16、TMEM=65536 words、IMEM=32768 words。m8 改为 MCOLS=8 与 TMEM=131072 words。不要把设计点、板卡、仿真默认值和 variant 的数字混在一个“默认架构”表里。

    SOURCE

    架构参数与微架构参数为何分开

    TOML 的 arch 描述程序依赖的容量、维度与功能；uarch 描述具体实现/时序选择，例如 MXU_IMPL、TMEM_IMPL、WIN、流水线长度。并非所有参数都应该改变程序语义，但它们可能显著改变时序和资源占用。

    CFG_HASH 与 numerics 用于核对程序、镜像和 bitstream 的契约。软件若按错误 D、格式或可选能力构建，不能期待驱动自动补救。自己实现时应提供只读能力寄存器，并在 RUN 之前拒绝不匹配，错误提示列出实际值和期望值。

    SOURCE

    板卡路径包含运输与控制，不等于模型算法

    Board/XdmaTransport 负责主机侧的数据运输和寄存器访问；BoardBackend 把模型的程序、数据与运行连接到设备。程序 loader、RUN/状态、参数、等待项和回读都有顺序要求。多个进程同时操作设备还需要设备级锁，不能仅靠 Python 的线程锁。

    自己写第一版驱动先实现“读设备标识 → 核对能力 → 写入已知数据 → 运行小程序 → 带 timeout 等待 → 读取结果”。逐步加超时恢复、错误状态和统计。完整 LLM chat 是最终集成用例，不是最早应调试的用例。

    SOURCE

    KV cache 不是 CPU 硬件缓存

    模型 KV cache 保存历史 token 的 key/value，是由软件显式管理的算法状态。它与普通 CPU 的 cache line、tag、替换策略和 MESI 权限状态不是同一概念。openTPU 的 program/image/quant cache 也可能指主机文件复用，不能据“cache”这个单词推出有 coherent cache RTL。

    如果你要添加多核共享硬件缓存，需要另外定义地址映射、行大小、私有/共享层级、目录状态、消息与瞬态，而不是扩充 KVCache 类就能完成。先学清现有系统的显式数据移动，再单独设计一致性扩展。

    SOURCE

    自己写一台小 openTPU：从契约到验证闭环

    用最小完整机器获得可定位的错误，而不是先堆完整模型。

    第一阶段：一个可执行规格

    先定义单 slice、有限 DRAM/TMEM/ACT、静态 shape、int8 格式和最少指令 LD、ST、QACT、MM、HALT。用独立的小解释器明确每条指令的读取/写入、对齐、越界、零值、舍入与完成语义。把合法与非法输入都写成可重复向量。

    验收标准是能手算的小矩阵与解释器逐项一致，错误程序会明确拒绝，而不是“跑起来且没有崩溃”。在这个阶段不需要 NoC、目录、复杂服务或完整 LLM。

    第二阶段：先做完全顺序 RTL

    实现 fetch/decode、单命令启动、busy/done、简单 SRAM 和数据通路。每条指令结束后导出 TMEM/DRAM，与规格逐位比较。将 FP 单元、量化器、MXU、DMA 各自做模块级测试，再连成 slice。

    第三阶段：增加银行、流水线与依赖

    第四阶段：编译器和真实工作负载

    加入描述符与简单 builder，先支持连续 load、广播 VOP 和 dot；随后增加循环、存储复用和分块 attention。为每次优化保留未优化路径作为对照。完整模型要分层比较 embedding、norm、每层输出与 logits，再看最终生成文本。

    先划清边界：openTPU 拥有什么，扩展系统又需要什么

    把真实项目的 slice、scratchpad、collective 与扩展教学的 NoC、cache、directory 分开，避免从名字猜硬件。

    一张图中，哪些盒子真的在 openTPU 里？

    scratchpad 为什么不是 cache？

    Scratchpad 是被显式寻址和搬运的存储。程序/编译器知道某个张量放在 TMEM 的什么位置，DMA 负责把 DRAM 数据搬进去。Cache 则按外部地址保存缓存行，自动判断 tag 是否命中，miss 时请求下层，并可能替换旧行。

    两者都可能用 SRAM/BRAM，但不能因为物理介质相同，就把 TMEM 称为 cache。要判断代码，应寻找 tag / valid / dirty / replacement / miss / refill 对应的控制与数据结构，而不只搜索文件名。openTPU TMEM 的核心机制是 bank、端口、复制、grant、写寄存和 bypass。其写入广播给读端口的各个副本，是同一逻辑存储的实现；这与多个独立 cache 中保存同一地址副本所需的一致性协议是不同问题。

    SOURCE

    collective 为什么不是一个 Mesh NoC？

    otpu_coll 等到所有 slice 请求同一 collective；GATHER 按 slice、行、列读取各 slice 的段，然后把输出写入所有 slice 的 TMEM。在仿真顶层直连接口中，gnt 取各 slice grant 的 AND，任一 slice 缺少端口资源就暂停共同推进。实际多 slice board 使用 hub/port 与缓冲及 credit，不能把这一组合 AND 当作所有板级实现。当前 YPCB 默认 S=1 且 BAR-only。BAR 只完成同步，不传输张量数据。

    这不是分布式五端口 router 的逐跳转发，也没有从这里自然推出缓存目录。把多个核连在一起，可以先用集中式互连、总线或专用 collective，再按规模和带宽需要改成 NoC。并非所有多核加速器都必须采用 Mesh。

    SOURCE

    NPU core 应该怎样定义，而不是怎样命名

    先为自己的 core 写一页契约：输入是标量指令、张量描述符还是任务队列？哪些数据属于该 core 的地址空间？什么时候接受命令？什么时候算完成？被背压时哪些状态保持？复位会不会丢弃已发出的外部事务？

    一个最小 NPU core 可以由“命令队列 + 解码 + 依赖检查 + DMA + MAC 阵列 + scratchpad + 完成队列”构成。暂时只支持固定尺寸矩阵乘，也能把接口闭环。真正让它成为可用系统的是可观察的完成与错误语义，不是先加上一个很大的阵列。openTPU 的 loader、halt、error、wr_idle/rd_idle 是值得逐条学习的系统契约。

    把一条交易写成一个布尔表达式

end

    FIFO 里真正必须保存的是哪几个状态

    本站 learn_elastic.sv 是一个深度为 2 的同步 FIFO：两个数据槽、头指针 head、尾指针 tail、占用数 occupancy。in_ready=(occupancy<2)，out_valid=(occupancy!=0)。写入与读出分别在自己的 fire 上发生，计数增加量为 put-pop。

    同时 put/pop 时占用数保持，但头尾都推进；空 FIFO 不允许 pop；满 FIFO 不允许 put。此练习没有组合空旁路，也不允许满队列在同拍 pop 时立刻补入新项。因此它很容易验证，却会在“满后持续交换”的边界产生一个恢复气泡。更高性能设计可以允许满时替换，但必须重新检查 ready 的组合路径与读写同地址语义。

    背压不只是让计数器停一下

    假设一条向量写有 lane mask、地址和数据。如果存储仲裁拒绝本次写，必须保持整组事务：不仅是数据，还包括地址、mask、最后一拍标记和事务标签。只停地址而让乘加流水线继续推进，会把下一组数据写到上一组位置。

    常见办法有两种：全流水线带 enable 一起冻结；或者在输出放 elastic buffer，让上游仍可运行，直到缓冲用尽。openTPU 的 TMEM 以执行单元为组仲裁，多个单元具有保持、排队或重放的不同实现，不能概括成“所有单元一律被 grant 全局冻结”。读这类代码时，必须逐个标出“请求生成”“请求被接受”“返回数据被消费”三个时间点。

    为什么组合 ready 链会拖慢时钟

    如果第 5 个模块的 ready 直接控制第 4 个，第 4 个再组合控制第 3 个，一条很长的 ready 传播链就跨过整个流水线。再让 valid 依赖下游 ready，很容易形成组合环。功能仿真看似能跑，布局后路径却过长。

    可用寄存切片、skid buffer 或提前计算的 credit 打断路径。代价是要为“ready 撤回尚未被上游看到的那几拍”预留存储。openTPU 在 shell 的异步 FIFO 中提供寄存写 ready 的 RWR 选择；这说明控制路径的形状会直接影响实现时序。先保证绝不覆盖未消费数据，再减少保守气泡。

    如何验证 FIFO，而不只看波形是否好看

    从一个可工作的 NPU core 写起：依赖、发射与完成

    最小 core 的五个边界

    从零实现时，可先定义五条边界：① host 提交任务；② loader 将程序放入 IMEM；③ sequencer 接受/发射命令；④执行单元完成数据写入；⑤ host 获得完成或错误。先规定每条边界的 valid/ready、payload、tag、reset 行为，暂时不要把整个系统写成一个巨大 always 块。

    命令格式可从 {opcode, src_addr, dst_addr, rows, cols, stride} 开始。第一版严格顺序执行，一条命令完成后才接受下一条。等矩阵运算、DMA 和错误路径都闭环，再增加重叠。openTPU 的调度窗口已经比这个起点复杂：不同执行单元可交叠，依赖检查负责保持规定结果。

    RAW、WAR、WAW 为什么必须区分

    RAW：B 读 A 尚未写出的结果；需要等 A 写入或提供正确旁路。WAW：B 与 A 写同一位置；结果次序不能颠倒。WAR：B 覆盖 A 尚未读完的数据；即使 A 不产生该位置的结果，也必须保护它。

    简单顺序读操作数、单结果写回的寄存器 core，可能用一个 busy 位数组挡住 RAW/WAW，且在发射时就已经取走源操作数。但张量指令会执行很多拍，整个区间仍在被读取，因此不能用“指令已发射”代表“所有源数据已读完”。openTPU 根据命令的内存 footprint 比较读写范围，而不是照搬通用 CPU 的寄存器 busy 位。

    SOURCE

    一个极小 busy-mask scoreboard 能教会什么

    learn_scoreboard.sv 为 8 个逻辑寄存器维护 busy 位；候选指令只有在 (busy & (reads | writes)) == 0 时才能发射。接受命令后预留目的寄存器；生产者在完成边沿清除对应位。练习故意没有同拍完成到发射的旁路，因而旧生产者完成这一拍，依赖者下一拍才 ready。

    它演示 RAW/WAW 和独立指令绕开等待的基本思想；不保存读者生命周期，也不支持推迟取源，所以不解决一般 WAR。它也没有 producer tag、重命名、取消、异常或多写回仲裁。完成必须来自真实在途生产者，不能把别人的 busy 位随便清掉。

    openTPU 的 range scoreboard 更接近任务图

    这里先解释基础 SEQ_WC=0 路径；当前 m4 目标 SEQ_WC=1 使用编译器生成的 WAITC wait entries 替代这套硬件范围比较，软件仍必须正确表达依赖。基础路径把一条命令映射成若干半开区间 [lo,hi)，例如 TMEM 输入只读区间、输出可写区间、DRAM 读/写区间和 ACT 范围。两个区间相交且至少一方写，才产生该地址空间上的依赖。空范围用一个不相交的表示处理。这样两个完全独立的张量操作可以同时运行。

    窗口里必须同时知道谁更老、谁依赖谁、谁已开始、谁已完成。openTPU 保存 age matrix，按执行单元寻找符合条件的候选。某些同单元依赖允许利用该单元内部顺序；VPU 又因多条指令可重叠而有特殊处理。读源代码时要看特殊条件，不能只画一个“scoreboard”盒子。

    存储微架构：bank、旁路、DMA 与跨时钟

    把“数据在哪里、谁能访问、何时可见”变成可检查的硬件契约。

    banking：把地址映射成端口压力

    对连续 word 地址，可采用 bank = address mod LANES、row = floor(address/LANES)。8 个 lane 访问连续 8 个 word 时恰好分布到 8 个 bank；8 个 lane 访问相隔 8 个 word 的地址则可能全部撞在一个 bank。提高 lane 数不自动提高有效带宽，地址模式与端口数同样重要。

    先写一张请求矩阵 need[unit][bank]，再把每个 bank 的已分配读/写数累加，只有所有所需资源均可满足，才 grant 该组事务。openTPU 对部分连续端口使用 barrel rotator，而不是一般的全连接 crossbar；这用布局约束换取更小的选择网络。

    SOURCE

    复制读端口、广播写与真实容量

    FPGA BRAM 的原生端口有限。若每个读端口需要独立地址，可以复制存储，再把每次写广播给所有副本。软件看到一个逻辑地址空间，物理上却有多份位存储，因此逻辑容量与实现容量不同。增加一个读端口可能增加大量 RAM 和写扇出。

    另一条路线是减少副本，允许访问竞争，加入分 bank 仲裁、子 bank、重放或多倍频访问。openTPU 为这些实现提供多种参数，部分明确标为 experimental。当前 m4 target 已选择 TMEM_IMPL=3 的单副本、子 bank、重放与 2×时钟访问；不要把模块默认的复制版当作当前板卡。比较它们要同时看面积、频率、端口冲突、重放率和端到端执行时间；不能只比较“RAM 数下降了多少”。

    SOURCE

    写入寄存之后，为什么还需要 bypass

    把仲裁后的写地址/数据寄存一拍，能减轻 grant 到大量 RAM 写端口的路径。但如果下一次读取恰好命中这条尚未落入 RAM 的写，直接取 RAM 就会读到旧值。必须把读地址与待写地址比较，命中时选择寄存中的新数据，形成旁路。

    不要把这个旁路与跨 cache 一致性混为一谈：这里解决的是同一逻辑 TMEM 中管线化写的可见性。自己实现时，要明确同拍读写同地址的 read-first/write-first 约定、多个待写级之间谁更新、lane mask 与 byte-enable 如何合并，以及持有读结果时是否允许旁路再次改变。先列清时序表，再写 mux。

    DMA：不是 memcpy 的一个大组合电路

    最小 DMA 需要读请求地址生成器、在途计数、返回缓冲、写目标地址生成器和完成逻辑。如果下层可乱序返回，就必须带 tag 并重排；如果约定每端口有序，仍要区分来自不同端口/客户的事务。突发拆分、对齐、尾部 mask 和超时也都属于接口的一部分。

    FIFO 深度须覆盖返回延迟与最大在途量，不能因为输出背压就让已接受的 DRAM 返回无处存放。一个简单安全办法是在发请求前预留返回槽位（credit）。openTPU shell 的内存通道与异步 FIFO 提供了有序提交/乱序槽位的实际工程例子，和单一同步 FIFO 的契约有显著区别。

    CDC：两级触发器不能直接同步一条总线

    单 bit、缓慢变化的控制信号可以经过同步器，降低亚稳态传播风险；多 bit 地址/数据各自独立过两级触发器，却可能被接收端拼成从未存在过的值。常见解决办法是握手保持整份数据，或使用双时钟 FIFO。

    openTPU 的 otpu_afifo 在写/读时钟域维护各自二进制指针，用 Gray 编码跨域同步后判断可见占用。Gray 编码使正常相邻指针只改变一位，但物理实现仍需要正确 CDC 约束、同步器识别和复位约定。同步后信息有延迟，因此 ready/used 必须保守：宁可短暂少用槽位，不能覆盖仍未被读出的数据。

    扩展设计课：从路由函数到一个能工作的 NoC

    本章 NoC 是自建扩展方案；openTPU 当前 collective 不是这个 Mesh。

    packet、flit、link、router、NI 各管什么

    Packet 是完整消息，如一次读请求或一条缓存行响应；flit 是链路/缓冲的流控单位，一个 packet 可能包含多 flit。Link 负责相邻节点传输；router 决定下一跳并仲裁出口；network interface (NI) 把本地协议转成 packet，再把返回消息交给正确的本地事务。

    即使 packet 只有一 flit，也要定义来源、目的、消息类、事务号和 payload。千万别把“网络宽度”直接当成“每拍有效应用带宽”：包头、竞争、注入限制、存储背压和时钟都会降低有效吞吐。网络也不自动提供内存一致性、缓存一致性或跨源全序。

    XY 路由只需要四个坐标，但只解决了下一跳

    本站 learn_xy_route.sv 先比较目的 X 与当前 X：不同则向东/西；X 相同再按 Y 向南/北；坐标完全相同则送本地。坐标约定为 Y 向南增大，端口编码为 0=LOCAL、1=E、2=W、3=S、4=N。

    每一跳把 Manhattan 距离减 1，故 4×4 Mesh 上最多走 6 跳。测试遍历 256 个合法源/目的对，总计检查 640 个转发跳。这个模块没有输入 FIFO、输出仲裁、下游 credit 或 packet 头尾状态，所以只是路由函数，不是一台 router。

    外部实现对照：FlooNoC 官方路由文档展示了维序路由及其确定性假设；此处的坐标方向与端口编码是我们自己的练习约定。

    五端口 router 的最小数据路径

    一个 2D Mesh router 常有本地、东、西、南、北五个端口。最小版本可以给每个输入一条 FIFO；查看头项目的地；为每个输出收集请求；每个输出仲裁一位赢家；crossbar 选择赢家数据；只有下游接受时才 pop 对应输入。

    request[input][output] = in_valid[input] && route(head[input]) == output
winner[output] = arbitrate(request[:,output])
pop[input] = exists output: winner[output]==input && downstream_ready[output]

    必须同时确保一个输出每拍最多一位赢家，一个输入每拍最多被一个输出消费。轮询仲裁的指针通常在成功传输后推进；若每次看见请求就转指针，受背压时的公平性与载荷稳定性可能被破坏。多 flit packet 还需规定出口是否锁定到尾 flit。

    credit、virtual channel 与 head-of-line blocking

    Credit 表示下游某缓冲还有多少空槽；发出一个 flit 就扣除，收到释放通知再加回。计数必须考虑链路飞行和 credit 返回延迟，不能拿“最近看到的 ready”当成永久可用空间。

    单输入 FIFO 的头 packet 如果被堵，后面即使要去空闲出口也无法超越，这叫 head-of-line blocking。Virtual channel (VC) 用同一物理链路承载多个独立队列/状态，帮助隔离阻塞和组织依赖，但需要 VC 分配、credit 计数和释放逻辑。加 VC 不自动无死锁，也不自动公平。第一版可使用单 flit 消息与独立请求/响应物理通道，把问题缩小后再增加复杂度。

    路由无环，不代表完整协议无死锁

    在通常的二维 Mesh、维序限制和对应流控假设下，先 X 后 Y 能避免网络 channel dependency 中的环。可是一致性协议还能产生另一种等待：请求占住缓冲等待响应；响应又等着被请求堵住的缓冲。此时路由函数再正确，系统仍可能停止进展。

    把请求、探针、响应分成独立网络或足够隔离的资源类别，是常见设计手段；但仍要画出“谁持有哪种资源、正在等待哪种资源”的图，检查是否成环。还要保证端点愿意消费必要的完成/ACK 消息。不能用有限流量仿真中“没卡住”来证明任意情况下都无死锁。

    如果给 openTPU 加 NoC，应先连哪一条边界

    先决定你想扩展的是 DRAM 访问、跨 slice 张量搬运，还是一种共享缓存系统。这三者需要不同协议。若只想将 GATHER 改成分布式传输，可把“源 slice、TMEM 段、目标 slice、事务号”封成消息；每端 NI 做 DMA 式读/写，并在全部目标确认后完成 collective。

    这样依然可以保持显式 scratchpad 语义，不必立刻引入 cache coherence。但要重新定义所有 slice 的同步、跨包重排、目标 TMEM 冲突、取消/复位和错误返回。先实现两端点单项传输，再扩大 Mesh，最后才考虑多在途与带宽优化。这是设计路线建议，不是上游已提供的接口。

    26 / MICROARCHITECTURE / 从概念写到 RTL

    扩展设计课：写一个 cache 之前，先把 miss 写清楚

    Cache 是地址、数据、替换与在途事务的控制器；本章不描述 openTPU 的既有 TMEM。

    地址分解、tag array 与 data array

    对行长 B 字节、组数 S 的简单 cache，地址可拆成 tag | index | offset。offset 选行内字节，index 选组，tag 判断该组的槽位当前保存哪条外部地址。每个 way 至少有 valid、tag、数据；write-back 还要 dirty，coherent cache 还要权限状态。

    第一版可直接映射、单端口、阻塞式、固定行长，只允许一个 miss。在一个 clock 接受 CPU 请求，下一拍查 tag；hit 再读/写数据；miss 若旧行 dirty，先写回，再取新行。即使这些功能很少，仍要定义请求保持、字节写 mask、错误和复位如何处理。

    一次 miss 至少有哪些状态

    可以从 IDLE → LOOKUP → WRITEBACK? → REFILL_REQ → REFILL_WAIT → RESP 开始。miss 时锁存原请求地址、操作、写数据和 mask，不能继续使用会变化的 CPU 输入。接收一条 refill 时验证它属于当前 miss，再装入 tag/data，最后响应原请求。

    若下层按多 beat 返回，就要记录 beat 计数与已到达 mask。只有完整缓存行已经可用，或接口明确支持 critical-word-first 的提前响应，才能开放后续命中。回填过程中该行不是一个普通可写 hit；这是引入 transient state 的最直观例子。

    MSHR 解决的是在途 miss 的身份与合并

    MSHR（miss status holding register）保存未完成 miss 的行地址、下层事务号、等待者、所需权限和回填进度。若新请求命中已有 miss 的同一行，可以合并为同一个下层请求；若是另一行，必须分配另一个槽位或背压。

    不能只有一个“miss 数量”而没有地址和身份。返回可能乱序，新请求也可能要升级权限；若 refill、eviction、probe 同时涉及同一行，控制器必须按协议串行化或进入明确瞬态。先从单 MSHR 正确版本开始，再把“独立行可并行”加入；不要把多 MSHR 当成简单扩大 FIFO 深度。

    一致性、内存顺序与软件同步是三个层次

    缓存一致性讨论同一地址副本的权限与值传播；内存一致性模型规定不同地址读写在观察者眼中允许哪些次序；同步原语利用原子操作、fence 或协议建立程序的先后关系。一个系统即使对每条行维持一致性，也可能允许不同地址的 store 被其他核以不同顺序看到。

    对自己的 NPU，显式 DMA + 软件所有权转移可能已经足够。例如 host 写输入、执行提交屏障、设备 DMA 读取、完成后 host 再读输出。若采用此路线，仍需说明 host cache 的 flush/invalidate 与平台 DMA API，不可把“没有 coherent cache”误解为“完全不需要可见性约定”。此处是通用设计方法，不表示当前 openTPU 已实现通用 CPU coherence。

    怎样从 scratchpad 走向 cache，又何时不该走

    Scratchpad 的优势是搬运和容量由编译器控制，便于规则张量计算；cache 的优势是对不规则和动态访问透明。增加 cache 会引入 tag、替换、miss 队列和不确定时延；再支持多核共享写，则需要一致性与网络资源。

    如果只想降低重复权重的 DRAM 读取，也许先做软件驻留、分块、双缓冲或专用只读缓冲就够了。若确实需要 cache，先做无共享写的只读 cache，再写 write-through/blocking 版本，最后才尝试 write-back 与 directory。每一步都要能量化命中率、额外访问、等待和容量代价。

    扩展设计课：directory_controller 怎样从状态表变成代码

    不要只背 MSI 三个字母，要跟踪正在等待谁、何时能够授予权限。

    目录保存的是分布式副本的知识

    对每条 cache line，目录至少要知道稳定权限状态、哪些客户端共享、谁拥有可写副本，以及是否有事务尚未结束。很多设计把行的 home 放到地址映射出的某个目录节点。Directory 通常不等于缓存数据本身：它首先管理权限，数据可能来自内存、owner 或另一个缓存。

    本站练习用 U 表示没有缓存副本、S 表示一个或多个共享只读副本、M 表示一个客户端独占可写。用 U 而不是 I 是为了避免把“目录无缓存副本”与“某个客户端缓存行无效”混淆。外部对照：gem5 的 MSI 目录教程展示了状态、sharers、owner 和瞬态；它是模拟器协议实现，不能直接当成可综合 RTL。

    GETS：读权限并不总能立即给出

    U 收到 GETS，可以请求数据并建立共享者；S 收到 GETS，可以增加共享者；M 收到另一客户端的 GETS，则不能直接相信内存仍是最新值，因为 owner 可能已修改。需要让 owner 提供最新数据并降级，然后才能完成新的共享读。

    练习 learn_directory.sv 省略全部数据路径，以“owner 的 ACK 已包含所需数据处理完成”为强前提。它在 M→S 时发出 probe_to_shared=1，等待 owner 对应 bit 的 ACK，再把旧 owner 与请求者一起加入 sharers。若同一个 owner 发 GETS，继续保持 M 权限即可。

    GETM：目标列表来自谁，而不是广播猜测

    U 收到 GETM 时可授予 M；S 收到 GETM，必须使除了请求者之外的 sharers 全部无效；M 收到另一个客户端的 GETM，要使旧 owner 交出最新数据与权限。请求者原本已经共享时，不必向它自己发送 invalidation。

    targets = sharers & ~onehot(requester)  // S → M
targets = onehot(owner)                 // M → M，且 owner 不同
pending = targets
remaining = pending & ~ack
// remaining==0 之后才可生成新的独占授予

    使用 mask 可以防止同一客户端的重复 ACK 被简单计数两次。真实系统还要匹配行地址、事务号和阶段，不能把任意旧 ACK 都接受为当前完成。

    瞬态为什么不是可有可无的细节

    目录已经发了 invalidation，但 ACK 尚未回来；旧共享者此时可能仍在处理本地读。这个区间既不是普通 S，也不是已经完成的 M。练习用 busy + pending + target_state 表示瞬态：稳定 metadata 暂存原值，拒绝新请求，直到所有目标完成才更新 metadata 并生成响应。

    工程系统通常不能把整台目录都锁住，于是使用每行 transient state 与事务缓冲（TBE），允许其他行继续服务。同一行后来的 GETS、GETM、eviction 或 writeback 可能排队、重试或触发特殊转移。gem5 的 MSI cache 状态源码可用来观察等待数据、等待 ACK 与替换期间的不同状态；本地简化练习没有实现完整协议。

    消息已发出、消息被接收、事务已完成是三件事

    probe_valid 不能只打一拍后就假设目标收到；需要网络接受握手或由 pending bit 持续表示仍需处理。在本站练习中，每个目标 bit 会保持到 ACK；ACK 的含义是该目标已经完成失效/降级，以及必要的数据交接，而不是“探针进入一个队列”。

    rsp_valid 同样保持到 rsp_ready。如果 grant 已经生成但请求者尚未接收，目录不能接纳下一条请求并覆盖响应字段。完整实现可能把响应放入队列、提前释放事务槽，但必须证明数据、权限与消息身份都不会被复用错误。不要靠固定等待 N 拍取代 ACK。

    如何自己写，并验证第一个 directory_controller

    1. 先写清两核单行、一次一个事务、可靠有序消息的前提；定义 U/S/M、GETS/GETM、probe、ACK、grant。
    2. 列出每个稳定状态 × 请求事件的表，逐格写目标集、待等事件和最终状态。
    3. 把状态分成 metadata、transaction、output 三组寄存器，组合逻辑只算下一状态与事件。
    4. 定向跑 U→S、S→S、S→M、M→S、M→M，逐一延迟 ACK 与响应接受。
    5. 接入两个真实 cache FSM 和数据内存，加入 store/load 的值验证；再扩到多行、多事务与网络。

    关键不变量：最多一个有效可写 owner；授予新 M 前其他副本已失效；读返回的值来自最近合法写；每次请求至多完成一次。在当前无数据练习中，只能直接检查控制与权限状态；“最新值”性质必须等你增加数据路径后再验证。

    从会读到会写：一条可执行的微架构训练路线

    用小系统建立正确性，再增加规模；每一步都留下可复查的证据。

    第 1 阶段：先把单元接口写成合同

    选一个向量加法或 MAC 单元，列出输入字段、输出字段、接受条件、背压规则、时延、复位行为、错误和完成。画三组逐拍表：连续输入、下游突然停止、复位发生在中途。

    可修改本站 FIFO：把深度从 2 参数化到 4；支持满时同拍 pop+put；加入输出寄存以打断 ready 链。每改一项，说明吞吐/时延/组合路径改变了什么，并扩充参考队列测试。不要把一个全绿输出当作接口规范的替代品。

    第 2 阶段：写一个严格顺序的矩阵 core

    采用固定 4×4 INT8 输入、INT32 累加，从双循环/单 MAC 顺序执行开始，再并行化。定义溢出、符号扩展、行列布局、尾块与 stride。配一个 Python/NumPy 精确整数参考，覆盖负数、极值、零、非整块尺寸和原地覆盖的禁止条件。

    等算术与地址都正确，再加入 DMA、片上双缓冲和流水。最后才引入窗口调度：此时你已经知道每条命令读写哪些内存位置，能计算 footprint，并理解为什么调度器必须保护它们。对照 openTPU 的分层，而不是一次复刻它的全部优化。

    第 3 阶段：让多端点通信，但保持语义简单

    从两个端点、单 flit、单在途开始，让 NI 发送带事务号的数据写；目标收到后返回 ACK，源等 ACK 才报告完成。加入可控随机背压、消息延迟和本地端口竞争。

    再用 XY 函数拼出 2×2 Mesh：每个输入 FIFO、每个出口仲裁、crossbar、逐跳接受。验证包不丢、不重、不被送错端点；检查每个被接受请求恰好有一个完成。扩大到 4×4 前，先把拥塞与复位场景跑清楚。本章提供了路由函数，未提供可直接综合的完整 Mesh。

    第 4 阶段：将目录控制扩为带数据的一致系统

    在本地两核单行目录基础上，加入每核 valid/state/data，加入共享内存数据，允许客户端在 M 状态写入。测试“核 0 写 7，核 1 读后必须见到 7”，再反向读写。通过延迟 probe、ACK 与数据返回，使旧 owner 在途写、失效和请求交错。

    然后增加多行地址与 per-line 事务身份，处理 evict、PutS、PutM、写回确认、目录条目回收。最后才引入有限队列与真实 NoC，重新检查协议资源死锁。每扩一步，都要重新明确哪些假设仍成立；省略了数据的控制练习不能直接升级为“完整一致性实现”。
